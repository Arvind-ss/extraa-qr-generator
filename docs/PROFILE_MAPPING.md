# Profile Mapping — legacy script → new profile system

Source: `legacy/qr_gen_3.py` (frozen copy of the script support was running,
last modified 2026-09-12). Twelve profiles live as commented blocks in its row
loop; one is active.

## Renderer generations

The repository contains output from **two** renderer generations. This matters
when judging whether an old image is a valid golden reference.

| Renderer | Source | Difference | Output size |
|---|---|---|---|
| `standard` | `qr_gen_3.py` | Crops to `(0, 40, 600, 520 + caption.height + 10)`, then **pads to a square**. Name row supports `top_pad=25`, `NAME_TRACKING=5`, `stroke_width=1`. | 660×660 typical, 712×712 when the name wraps, 600×600 with no name row |
| `standard_v1` | `qr_gen.py` | Hardcoded `crop((0, 40, 600, 640))`, **no square-padding step**. No `top_pad`, no tracking, no stroke. | always 600×600 |

For a card with **no name row**, the two differ only by an 8 px vertical shift
(v1 crops to a fixed 640; the current one pads 583 → 600 with `(600-583)//2 = 8`).
Everything else — module grid, ink columns 83–516, run lengths — is identical.

**Consequence:** `pos_machine_qrs/**` was generated by `standard_v1` and is *not*
a golden reference for the current renderer. Verified by rendering with
`qr_gen.py`, which reproduces those files byte-for-byte. The two POS fixtures in
`tests/golden/` are tagged `"renderer": "standard_v1"` and excluded from the
current-renderer test. Do not "fix" the renderer to match them.

The Extraa Cards corpus (`B0004`–`B0007`, `Brigade`, `sample_copy`) *is* current:
**2,000 cards verified byte-identical**.

A third generation was prototyped on 2026-09-12 (Extraa logo, `#4C2B83`/`#FCB712`,
rounded eyes, ECC-H — see `design_options.png`, "option D") and **was not merged**.
If adopted it becomes renderer key `"branded"`.

### Notes on individual profiles

- **#6 Zomato** passes `create_caption_image(..., 400)`. That argument has never
  done anything — every width in the renderer is hardcoded to 600/580. Its output
  is 600 px wide like everything else.
- **#7 Sangeetha** prints `TEST-` before the name. Looks like leftover debugging;
  confirm before migrating.
- **#9 POS** last ran on `standard_v1`. Migrating it to `standard` will shift
  every card 8 px vertically. That is a visible change and needs sign-off.
- **#10 Event Ticket** is the only profile with non-template filename logic
  (`if filename.endswith(" 1/1")`). It becomes a named entry in the filename
  transform whitelist, not a new renderer.
- **#13 Collective Culture** produces an identical QR for every row; `{qr_code}`
  only keeps filenames unique.
- **#6, #7, #9** build filenames from `{name}`, free text. Shipped POS output
  already contains filenames like `M41 - I520.png`. These need the filename
  sanitizer (path traversal, Windows reserved names) before they are re-enabled.

## Output format

Every profile writes **JPEG bytes into files named `.png`** (`format='JPEG'`,
`legacy/qr_gen_3.py:117`; the `format='PNG'` line above it is commented out).
Confirmed against every reference image on disk. Preserved by decision, recorded
here so nobody "fixes" it by accident.

## Printed text size change — 2026-09-13

The name and code printed on the card were enlarged by request:

| | Was | Now |
|---|---|---|
| Name (upper row) | 36px | **48px** |
| Code (lower row) | 60px | **80px** |
| Card, one-line name | 660×660 | **688×688** |
| Card, no name row | 600×600 | 600×600 (unchanged) |

**This deliberately breaks byte parity with the ~2,000 cards already shipped.**
Batches printed before this date will not match batches printed after it. That
was an accepted trade, not a regression.

Nothing else moved. The QR is untouched — the caption is pasted at a fixed
`y=520` and grows downward, so it can never reach the modules. Measured: the
top quiet zone is still 15px at every text size tried, and a card with no name
row is still exactly 600×600.

The sizes are `NAME_SIZE` and `CODE_SIZE` in `qrgen/renderers/standard.py`.

### The historical corpus still passes

The golden and differential tests pin the renderer back to 36/60, so the
~2,000 shipped cards are still verified byte-for-byte on every run. The point
of that corpus is unchanged: it proves the renderer can still reproduce
anything already in the field. Two further tests, marked `current_sizes`,
check what it produces *today*.

Long store names wrap to three lines at 48px where they used to take two,
making those cards taller. Card height has always varied with the name, so
this is more of the same, not a new behaviour.

## Typeface change — 2026-09-13

The card now prints in **Roboto Regular** (`rob.ttf`). It previously used
`rob_batch.ttf`, which despite its filename is **Geist Mono Light** — worth
knowing, because the name implies Roboto and it never was.

| | Geist Mono 48/80 | Roboto 48/80 |
|---|---|---|
| Card, one-line name | 688×688 | **697×697** |
| Card, no name row | 600×600 | **606×606** |
| Card, wrapping name | 763×763 | 763×763 |
| `RDFXRN` width | 288px | 302px |
| A long store name | 3 lines | **2 lines** |

Roboto's line box is taller, so every card grows a few pixels; but it is
narrower per glyph, so long names wrap onto fewer lines. A no-name card — the
POS/Zomato shape — is no longer exactly 600×600.

Both typefaces ship. `name_font` and `code_font` are profile fields, validated
against the files actually present in `assets/fonts/`; a filename that is not a
bare name in that directory is refused, so a profile cannot point the renderer
at an arbitrary path.

The name row and code row take separate font settings and can differ.

### The historical corpus still passes

The golden and differential tests pin the renderer back to `rob_batch.ttf` at
36/60 — the exact typeface and sizes every shipped card was printed with — so
all ~2,000 are still verified byte-for-byte on every run.
